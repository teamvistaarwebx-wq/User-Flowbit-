Flowbit · AI Architecture1
⌐ 1 · The big picture BUILT

One gateway for all AI: Arc and Meetings minutes both call the same askClaude(), so caps, redaction and usage logging apply everywhere. Only ai-client.ts talks to Anthropic.

Three outside services for meetings: Recall.ai records, Sarvam transcribes, Claude writes the minutes. Recall and Sarvam call back through webhooks; the 15-minute cron catches anything missed.

Flowbit · AI Architecture2
⌐ 2 · Arc AI: architecture BUILT

Monthly caps (Console)

Requests per workspace per month (IST): free 0, trial 50, paid 500, comped / internal 500, test 50. Staff change them in Console → Settings → Arc AI.

Redaction

Salary, bank and PAN details are stripped from the system prompt and the user prompt before anything leaves Flowbit (lib/ai-redact.ts).

Never blocks the user

The gateway never throws. If AI is unavailable the user still gets a template draft (templates.ts) and a note explaining why.

⌐ 2 · Arc AI: user flow in detail BUILT

Example: "Outline a project"

1
User opens Arc (/app/arc) and clicks Outline a project. A dialog asks for the project name, goal and start date (or an existing project).
2
The browser calls the server action draftOutline. It checks the arc.use permission and, for an existing project, that the user may open it.
3
The action builds the prompt: project name, goal, workspace team names, and the exact JSON shape wanted (3–6 milestones, 2–5 tasks each).
4
askClaudeJson() → askClaude(): key check → plan cap → monthly count → redaction → callClaude() on the draft tier (Claude Sonnet 5.5).
5
The reply is parsed as JSON and checked with zod. If it is invalid, Arc asks once more with "reply with only the JSON". The retry is logged but not counted against the cap.
6
Tokens are logged in AiUsage. The draft is saved as an ArcRun (status draft, source ai or template).
7
The page refreshes and shows the draft card. Nothing is created yet. The user reviews and edits it.
8
Apply → apply-actions.ts creates the project, milestones and tasks. Discard → the run is marked discarded and nothing is created.

⌐ 3 · Meetings AI: architecture BUILT
Which AI model gets the transcript? Today the transcript goes to Claude Sonnet 5.5 (claude-sonnet-5-5, the "draft" tier) through the same AI Gateway as Arc, max 4,000 output tokens, and it counts as one Arc AI request. Decided for the new design: it goes to the organiser's default model, then the workspace default, then Claude Haiku (pages 8 and 11). Sarvam (transcription) and Recall (bot) do not change.

⌐ 3 · Meetings AI: user flows in detail BUILT

Flow A · The bot joins the meeting

1
Create the meeting (title, time IST, attendees, link). Paste a Meet / Zoom / Teams link, or leave it empty. If the organiser has connected Google Calendar, saving creates a Google Meet link automatically (the form says so; if not connected it shows a Connect button).
2
On the meeting page, the Meetings AI card shows Send notetaker (needs: link, meeting not ended, user is a participant, Meetings AI on the plan, Recall keys on the server). User confirms.
3
Server checks: link is Meet/Zoom/Teams, enough hours left for the scheduled length, and locks the meeting so two clicks can't book two bots.
4
Flowbit asks Recall.ai to book a bot with the meeting link. Booked 10+ minutes ahead → it joins at the start time; later → it joins now. Every attendee gets a consent email (who records, why, how long it is kept). Status: Booked. "Call off notetaker" cancels it.
5
At start time the bot opens the link as a guest named Flowbit Notetaker. The host must admit it (it waits up to 10 min, and leaves if nobody joins in 10 min). It posts a chat message that it is recording. Status: In the call.
6
Meeting ends → Recall sends a done webhook → Flowbit downloads the mp3, saves it as the meeting's recording and starts transcription. Backups: Fetch from bot button and the cron (after 20 min, up to 5 tries).
7
From here it is the shared pipeline (steps 8–11 on the right).

Flow B · The user records it themselves

1
User records the meeting another way: Meet/Zoom's own record button, a phone recorder for an in-person meeting, any tool. Up to 2 hours, 200 MB.
2
On the meeting page → Upload recording. The browser reads the length; the server checks the hours left this month.
3
With S3/R2 storage the file goes straight to the bucket (signed PUT); otherwise through the server. Then transcription starts.

Shared pipeline (both flows)

8
Sarvam transcribes (Hinglish code-mix, speaker labels). It calls /api/webhooks/sarvam with a secret token; Flowbit then fetches the transcript. Backups: Check now button and the cron.
9
The transcript is saved and the audio hours are counted against the monthly limit.
10
Claude gets the transcript + title, date, attendees, agenda and returns JSON: agenda, notes, decisions, action items (owner as spoken, due date only if said). Owners are matched to workspace members.
11
Minutes go into the notes, the agenda (if empty) and draft action items. The organiser is notified. Later: rename speakers, Draft minutes again, delete recording/transcript; both auto-delete after the retention period (default 90 days).
If AI is off or the cap is reached, the notes quote the transcript and say why. Upload sends no consent email (the user recorded it themselves).

⌐ 5 · Proposed: multi-model AI gateway PROPOSED

Why a catalog key

The user picks gemini-flash, never a raw model id. Upgrading the model behind it changes one catalog line, not every user's setting. Staff can switch a model off during an outage.

Why adapters

Same idea as TranscriptionProvider (Sarvam) and MeetingBotProvider (Recall) that already exist. Adding our own Ollama model later = one adapter + one catalog line.

What changes for features

Arc and minutes stop passing a tier and pass the resolved model. askClaude → askAi. JSON checks, redaction and templates stay. Transcription (Sarvam) and the bot (Recall) are not affected.

⌐ 6 · Proposed: credits, wallet & billing PROPOSED

Tokens inside, credits outside

Providers bill Flowbit in tokens, and each model has its own price per token (input and output priced differently). Customers see and buy credits, Flowbit's own unit. The gateway converts tokens to credits using each model's price, so cheaper models use fewer credits and Flowbit never sells below cost.

Where credits come from

SourceHowExpires
IncludedWith the plan: free 0, trial flat, paid N per seat (same formula as meeting hours)Monthly reset (IST)
AI credits add-onPaid per seat, next to meetings_ai in ADD_ONS, on the Razorpay subscriptionMonthly
Top-up packs (later)One-time purchase when a workspace runs out mid-month12 months

Spent in order: included → add-on → top-up (soonest to expire first). Pooled for the whole workspace (seats × N), like Meetings AI hours.

Data changes

CollectionChange
AiUsage+ provider, modelKey, costUsd (what Flowbit paid), credits (what we charged) → margin reports for free
AiCreditLedger (new)One row per grant (monthly, add-on, top-up) and per debit. Audit trail for disputes.
Member / Org settingsDefault model per member; allowed models + default per workspace
Console settingsCatalog overrides: enabled, prices, credit value, USD→INR rate

Rules for safe charging

  • Check before, charge after: estimate from max tokens, call, then debit the real amount. A tiny overdraft is acceptable.
  • Atomic debit ($inc with a condition) so two requests at once can't both spend the last credits.
  • JSON retries: Flowbit absorbs them (the model's fault); failed calls and refusals are never charged.
  • Outage: template fallback + a "Try with another model" button, never a silent switch.
  • Self-hosted model: no per-token bill, so give it an internal price (GPU cost) and credits still work.

What does NOT use credits

Meeting transcription (Sarvam) and the bot (Recall) stay on the hours limit. Only the minutes step (text AI) spends credits. So a bot-recorded meeting uses hours + credits.

Privacy: adding Google and OpenAI means listing them as subprocessors (modules/marketing/legal/providers.ts) and updating the privacy policy. Redaction runs for every provider.

General rules

✅ Do
Log the real cost of every request from day one (Phase 1)
Test each new provider with a small internal group before releasing it to all customers
Add Google and OpenAI to the subprocessor list and privacy policy before launch
Keep redaction and JSON validation for every provider
Build our own Ollama model last, once usage volumes are known
❌ Don't
Launch paid credits before there is cost data
Let customers bring their own API keys yet (complicates billing and support)
Send data to new providers before the legal pages are updated
Assume every model follows the JSON format equally well; test each one
Start the self-hosted model now (GPU servers are expensive if barely used)
In one line: workspace credit pool · minutes use the organiser's model (fallback Haiku) · Flowbit absorbs retries · no silent provider switching · top-ups expire after 12 months · set credit prices only after 2–4 weeks of real cost data.
